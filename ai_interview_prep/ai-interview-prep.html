1. Distributed Systems & System Design Highest ROI — practice first

Scalability trade-offs, consistency models, and the standard "design X" interview format.

1.1 Explain CAP theorem in your own words with a concrete example of choosing CP vs AP.Theory

Under a network partition, a distributed system must choose between Consistency (every read sees the latest write) and Availability (every request gets a response, possibly stale). CP example: a distributed lock service (etcd/ZooKeeper) — must refuse requests rather than risk two nodes believing they hold the same lock. AP example: a shopping cart service — better to let users keep adding items (possibly reconciled later) than to reject requests during a partition.

1.2 Strong consistency vs eventual consistency vs read-your-writes — when does each matter?Consistency Models

Strong: every read reflects the most recent write (needed for bank balances, inventory counts near zero). Eventual: replicas converge over time, acceptable for things like social media like-counts or search index updates. Read-your-writes: a middle ground often needed for good UX — a user should immediately see their own comment/post even if other users see it with a delay (achieved via session stickiness or routing reads to the primary shortly after a write).

1.3 How do you shard a database, and what are the common sharding key strategies?Scalability

Range-based (good for range queries, risk of hot shards for sequential keys like timestamps), hash-based (even distribution, poor range queries), and directory-based (a lookup service maps keys to shards, flexible but adds a dependency/SPOF risk unless replicated). Discuss re-sharding pain (consistent hashing minimizes data movement when adding/removing nodes) and cross-shard queries/joins as a major downside requiring denormalization or a separate analytics store.

1.4 Design a URL shortener (classic prompt) — outline your approach.System Design Prompt

Expected structure: (1) clarify requirements & scale — reads:writes ratio (typically read-heavy), custom aliases, expiry, analytics; (2) API design — POST /urls, GET /{code}; (3) ID generation — base62 counter, or hash+collision-check, discuss distributed unique ID generation (Snowflake-style) if multiple write nodes; (4) storage — key-value store (DynamoDB/Redis) fits access pattern well; (5) caching layer for hot redirects; (6) scaling reads via CDN/edge caching for redirects since they're idempotent and cacheable.

1.5 Design a rate limiter for a public API used by many services (like this file's exercise, but at system scale).System Design Prompt

Discuss algorithms: token bucket (allows bursts, smooth refill), sliding window log (accurate, memory-heavy), sliding window counter (good approximation, cheap). At scale, per-instance in-memory counters don't work across a fleet — need a shared store (Redis) with atomic increment+expire (Lua script or INCR+EXPIRE), or a dedicated rate-limiting service at the API Gateway layer. Cover what happens under Redis outage (fail-open vs fail-closed trade-off).

1.6 How would you design a notification system that fans out to email, SMS, and push, handling millions of users?System Design Prompt

Producer publishes a "NotificationRequested" event to a queue/stream; a fan-out worker or per-channel consumer groups pick it up. Each channel (email/SMS/push) is its own consumer with its own retry/backoff and third-party rate limits (SES, Twilio, FCM/APNs). Discuss deduplication, user preference/opt-out checks before sending, and prioritization queues (transactional vs marketing) so critical notifications aren't delayed by bulk sends.

1.7 What is consistent hashing and why is it used over simple modulo hashing?Theory

Simple modulo (hash(key) % N) re-maps almost every key when N (node count) changes, causing massive cache/data churn on scale up/down. Consistent hashing places nodes and keys on a hash ring; each key belongs to the next node clockwise. Adding/removing a node only remaps the keys between it and its neighbor, minimizing redistribution. Virtual nodes address uneven load distribution across a small number of physical nodes.

1.8 Explain leader election and how it's used in distributed systems (e.g., Raft/etcd/ZooKeeper).Consensus

In systems needing a single coordinator (e.g., a primary DB node, a job scheduler), nodes run a consensus algorithm (Raft, Paxos) to agree on one leader, tolerating node failures. Raft in brief: nodes are Follower/Candidate/Leader; a Candidate requests votes; majority quorum wins leadership for a term; heartbeats maintain leadership; failure to hear from leader triggers a new election. This underlies etcd/Consul, which many microservices systems use for distributed locks and config.

Design Exercise 1.1 — Design a Distributed Job Scheduler

  • Requirements: schedule millions of one-off and recurring jobs; at-least-once execution; horizontal scalability; no single point of failure.
  • Deliver: high-level architecture diagram (verbal/whiteboard), data model for jobs, how workers claim jobs without double-execution (leasing/locking), and how you'd handle a worker crashing mid-job.
Model Solution / ApproachReveal

Data model: a jobs table with columns like id, run_at, cron_expr (nullable), status (pending/claimed/running/done/failed), claimed_by, claimed_at, lease_expires_at, attempts. Recurring jobs store their cron expression and get a new row (or a computed next run_at) generated after each run.

Claiming without double-execution: workers poll for jobs where run_at <= now() AND status = 'pending' (or status='claimed' AND lease_expires_at < now() for expired leases), and claim atomically with a conditional update: UPDATE jobs SET status='claimed', claimed_by=$workerId, lease_expires_at=now()+lease_duration WHERE id=$id AND status='pending' RETURNING *. The WHERE status='pending' guard means only one worker's UPDATE affects a row — this is the same leasing pattern used by systems like Sidekiq/Celery/SQS visibility timeouts.

Worker crash mid-job: the lease (lease_expires_at) means if a worker dies without marking the job done, another worker eventually sees the expired lease and reclaims it — this naturally gives at-least-once execution. The job handler itself must be idempotent (or use a completion/dedup check) since it may run more than once.

Scale & no SPOF: the scheduler is just workers polling a shared, horizontally-scalable data store (Postgres with row-level locking, or a purpose-built store like DynamoDB) — there's no single "scheduler brain" that's a single point of failure. Discuss sharding the jobs table by run_at bucket or job type if polling contention becomes a bottleneck at very high volume, and using SKIP LOCKED (Postgres) to let many workers poll concurrently without blocking each other.

Design Exercise 1.2 — Design a Real-Time Collaborative Document Editor's Backend

  • Cover: conflict resolution (OT vs CRDTs), how edits propagate (WebSocket fan-out), persistence strategy (snapshot + operation log), and horizontal scaling of the real-time layer (sticky sessions vs pub/sub backplane like Redis).
Model Solution / ApproachReveal

Conflict resolution — OT vs CRDTs: Operational Transformation (used by early Google Docs) transforms each incoming operation against concurrent operations so they can be applied in any order and converge, but requires a central server to sequence/transform operations correctly and is notoriously hard to implement correctly for rich document structures. CRDTs (e.g., Yjs, Automerge) design the data structure itself so concurrent updates merge deterministically without a central arbiter — simpler to reason about and works better offline-first, at the cost of some memory overhead for tombstones/metadata. Most new systems (Figma-style, modern editors) favor CRDTs.

Edit propagation: each client holds a WebSocket connection to an edit server; local edits apply optimistically to the local CRDT/OT doc, then broadcast to the server, which relays to all other connected clients editing the same document (a "room"). For horizontal scaling of the WebSocket layer, sticky sessions alone don't work once you have many server instances — use a pub/sub backplane (Redis Pub/Sub, or a message broker) so a client connected to server A gets updates originating from a client on server B.

Persistence: store periodic snapshots of the full document state plus an append-only operation log since the last snapshot (similar to event sourcing) — this lets you reconstruct current state fast (snapshot + replay recent ops) without replaying the entire history, and supports undo/version history features.

Scaling further: partition documents/rooms across server instances (consistent hashing on document ID) so a given document's traffic is handled by one primary instance at a time, avoiding needing every instance to relay every edit for every document.

2. Microservices High ROI — same patterns as System Design

Service boundaries, communication patterns, data consistency, and failure isolation.

2.1 How do you decide service boundaries in a microservices architecture?Design

Align boundaries with business capabilities / bounded contexts (Domain-Driven Design), not technical layers. Each service should own its data and be independently deployable. Signals a boundary is wrong: services always deploy together, high chattiness between two services, shared database tables across teams. Discuss trade-off: too fine-grained → distributed monolith with network overhead and orchestration complexity.

2.2 Synchronous (REST/gRPC) vs asynchronous (message queue/event) communication between services — when to use each?Communication

Sync: simple request/response, need immediate result, low fan-out (e.g., checking inventory before confirming an order). Downsides: tight coupling to availability, cascading failures, latency stacking. Async (Kafka/RabbitMQ/SNS-SQS): decouples producer/consumer lifecycles, natural buffering under load, supports event-driven architectures and eventual consistency, but adds complexity (ordering, idempotency, debugging, eventual visibility). Real systems mix both: sync for user-facing reads, async for cross-service side effects.

2.3 What is the Saga pattern and why is it needed in microservices?Data Consistency

Since each microservice has its own database, distributed ACID transactions (2PC) don't scale well across services. A Saga breaks a business transaction into a sequence of local transactions, each publishing an event/command that triggers the next step. If a step fails, compensating transactions undo prior steps. Two coordination styles: choreography (services react to each other's events, no central brain) vs orchestration (a central saga coordinator/orchestrator directs each step, easier to reason about but a new dependency).

2.4 Explain the Circuit Breaker pattern and where it fits in a microservices call chain.Resilience

Wraps calls to a downstream dependency; tracks failure rate. States: Closed (calls pass through normally) → Open (after threshold of failures, calls fail fast without hitting the downstream, giving it time to recover) → Half-Open (allow a trial request to test recovery). Prevents cascading failure/thread exhaustion when a downstream service is degraded. Pair with timeouts, retries with backoff+jitter, and bulkheads (isolating resource pools per dependency).

2.5 How do you handle service discovery and configuration in a microservices deployment?Infrastructure

Options: client-side discovery (services query a registry like Consul/Eureka directly), server-side discovery (a load balancer/service mesh like Kubernetes Services + kube-proxy, or Istio/Linkerd, handles routing transparently). In Kubernetes-native setups, DNS-based service discovery + a sidecar mesh proxy is now the common default over hand-rolled registries. Config: externalize via env vars, ConfigMaps/Secrets, or a centralized config service, never bake environment-specific config into images.

2.6 What is the API Gateway pattern, and what cross-cutting concerns does it handle?Architecture

A single entry point that routes external requests to internal services, and centralizes cross-cutting concerns: authentication/authorization, rate limiting, request/response transformation, aggregation (BFF-style composing multiple service calls into one response), TLS termination, and observability. Trade-off: risk of becoming a bottleneck or "God object" if business logic leaks into it — keep it thin.

2.7 How do you maintain data consistency and avoid duplicate processing when consuming events at-least-once?Reliability

Most brokers (Kafka, SQS) provide at-least-once delivery, so consumers must be idempotent: dedupe using a unique event/message ID stored with the processing result (idempotency key table), or design operations to be naturally idempotent (upserts vs increments). Also discuss the outbox pattern: writing the DB change and the "event to publish" in the same local transaction, then a relay process publishes from the outbox table, avoiding the dual-write problem.

Coding Exercise 2.1 — Idempotent Payment Consumer

Write a Node.js consumer function that processes PaymentCompleted events from a queue. Given the broker delivers at-least-once, implement idempotency so processing the same event twice never double-credits an account. Use an in-memory store (Map) to simulate a DB idempotency table for the exercise, but design the interface so it could be swapped for Postgres/Redis.

Model SolutionReveal 
interface PaymentCompletedEvent {
  eventId: string;      // unique per event, provided by the broker/producer
  accountId: string;
  amount: number;
}

interface IdempotencyStore {
  hasProcessed(eventId: string): Promise<boolean>;
  markProcessed(eventId: string): Promise<void>;
}

class InMemoryIdempotencyStore implements IdempotencyStore {
  private seen = new Set<string>();
  async hasProcessed(eventId: string) { return this.seen.has(eventId); }
  async markProcessed(eventId: string) { this.seen.add(eventId); }
}

async function handlePaymentCompleted(
  event: PaymentCompletedEvent,
  store: IdempotencyStore,
  creditAccount: (accountId: string, amount: number) => Promise<void>
) {
  if (await store.hasProcessed(event.eventId)) {
    // Already handled this exact event — broker redelivered it. No-op.
    return;
  }

  await creditAccount(event.accountId, event.amount);
  await store.markProcessed(event.eventId);
}

Why this works: the dedupe check is keyed on the event's own unique ID (not on account/amount), which is the correct key for at-least-once delivery — the broker may redeliver the exact same event, and we must recognize "I've already applied this one" regardless of how many times it arrives.

The subtlety interviewers probe for: in a real system, the hasProcessed check, creditAccount, and markProcessed need to happen atomically (e.g., in one DB transaction, or via a unique constraint on eventId in the same table as the balance update) — otherwise a crash between crediting the account and marking it processed re-triggers a double-credit on redelivery. This is the classic argument for combining the idempotency key with the business write in a single transaction rather than two separate stores.

Coding Exercise 2.2 — Circuit Breaker Implementation

Implement a minimal circuit breaker class (TypeScript) wrapping an async function, with configurable failure threshold, reset timeout, and half-open trial. No external libraries (no opossum) — write the state machine yourself. Include unit tests for the Closed→Open and Open→Half-Open→Closed transitions.

Model SolutionReveal 
type State = 'CLOSED' | 'OPEN' | 'HALF_OPEN';

class CircuitBreaker<T> {
  private state: State = 'CLOSED';
  private failureCount = 0;
  private nextAttempt = 0;

  constructor(
    private fn: (...args: any[]) => Promise<T>,
    private failureThreshold = 3,
    private resetTimeoutMs = 5000
  ) {}

  async call(...args: any[]): Promise<T> {
    if (this.state === 'OPEN') {
      if (Date.now() < this.nextAttempt) {
        throw new Error('Circuit is OPEN — failing fast');
      }
      this.state = 'HALF_OPEN';
    }

    try {
      const result = await this.fn(...args);
      this.onSuccess();
      return result;
    } catch (err) {
      this.onFailure();
      throw err;
    }
  }

  private onSuccess() {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }

  private onFailure() {
    this.failureCount++;
    if (this.state === 'HALF_OPEN' || this.failureCount >= this.failureThreshold) {
      this.state = 'OPEN';
      this.nextAttempt = Date.now() + this.resetTimeoutMs;
    }
  }
}

Why this works: the breaker fails fast while OPEN (no call to fn at all), avoiding piling up slow/timed-out calls against an already-struggling dependency. Once resetTimeoutMs elapses, exactly one trial call is allowed through in HALF_OPEN — a single failure there immediately re-opens the circuit (no need to hit the full threshold again), while a success resets fully to CLOSED.

Test cases to write: (1) N consecutive failures flips CLOSED→OPEN; (2) calling during OPEN before the timeout throws immediately without invoking fn; (3) after the timeout, the next call is allowed through (HALF_OPEN) and a success returns to CLOSED; (4) a failure during HALF_OPEN goes straight back to OPEN and resets the timer.

3. API Design & Backend Engineering (REST) Mostly judgment — fast to lock in

Resource modeling, versioning, error handling, and pragmatic REST discipline.

3.1 What makes an API "RESTful"? Which constraints do most real-world APIs relax?Fundamentals

Roy Fielding's constraints: client-server, statelessness, cacheability, uniform interface, layered system, and (optionally) code-on-demand. In practice, most "REST APIs" skip HATEOAS (hypermedia-driven discoverability) and just use resource-oriented URLs + HTTP verbs + JSON — which is really "REST-ish"/RPC-over-HTTP. Interviewers want you to recognize this distinction, not just recite the term.

3.2 How do you design resource URLs and choose HTTP verbs/status codes correctly?REST Conventions

Nouns not verbs (/orders/:id, not /getOrder). Verbs: GET (safe/idempotent), POST (create, non-idempotent), PUT (full replace, idempotent), PATCH (partial update), DELETE (idempotent). Status codes: 200 (OK), 201 (Created, with Location header), 204 (No Content), 400 (bad request/validation), 401 (unauthenticated), 403 (unauthorized), 404 (not found), 409 (conflict, e.g., optimistic lock failure), 422 (semantically invalid), 429 (rate limited), 500/503 (server/unavailable).

3.3 How would you design API versioning, and what are the trade-offs between approaches?Versioning

URI versioning (/v1/orders) — simple, cacheable, but clutters URLs and encourages big-bang breaking versions. Header/media-type versioning (Accept: application/vnd.api.v2+json) — cleaner URLs, harder to test manually/discover. Additive/non-breaking evolution (adding optional fields, never removing/renaming) avoids versioning entirely for a long time and is generally preferred until a genuinely breaking change is unavoidable.

3.4 Design pagination for a large collection endpoint — offset vs cursor-based, trade-offs?Pagination

Offset/limit (?page=3&limit=20): simple, allows jumping to arbitrary pages, but breaks under concurrent inserts/deletes (items shift between pages) and gets slow on large offsets (DB still scans/skips rows). Cursor-based (?after=<opaque_id>): stable under mutation, efficient (indexed seek), but no random page access. Recommend cursor-based for high-write, high-scale collections (feeds, logs); offset is fine for small, relatively static admin tables.

3.5 How do you design a consistent error response format across an API?Error Handling

Standardize a shape like { error: { code, message, details?, traceId } } across all endpoints, distinct from the success payload shape. Use machine-readable code (e.g., VALIDATION_FAILED) so clients can branch logic without parsing message strings (which may change/be localized). Include a correlation/trace ID for support/debugging across microservices. Never leak stack traces or internal implementation details to clients in production.

3.6 How do you handle authentication/authorization in a REST API — sessions vs JWT?Security

Sessions: server-stored state (Redis), easy revocation, requires sticky sessions or shared store across instances. JWT: stateless, self-contained, scales horizontally without shared session storage, but harder to revoke before expiry (mitigations: short expiry + refresh tokens, or a denylist). For microservices, JWTs (often signed by a central auth service, verified by each service without a round trip) are common; discuss token refresh flow and where to store tokens on the client (httpOnly cookies vs localStorage — XSS/CSRF trade-offs).

3.7 What is idempotency in the context of REST APIs, and how do you support idempotent POST requests (e.g., for payments)?Reliability

GET/PUT/DELETE are idempotent by spec; POST is not, but clients need idempotent "create" semantics to safely retry after a timeout (did the payment actually go through?). Common solution: client generates an Idempotency-Key header; server stores the key with the result of the first successful processing, and returns the cached result for duplicate keys instead of reprocessing.

3.8 How would you approach rate limiting and throttling for API consumers with different tiers (free vs paid)?API Governance

Attach limits to API keys/accounts rather than IPs (multiple users behind NAT/shared IP). Return 429 with Retry-After and rate-limit headers (X-RateLimit-Limit/Remaining/Reset) so clients can back off intelligently. Tiering usually enforced at the gateway layer, with limits configurable per plan stored alongside account/billing data.

Coding Exercise 3.1 — Build a REST CRUD API with Validation

Using Node.js + Express (or Fastify) and TypeScript, implement /tasks resource endpoints: list (paginated), get by id, create, update, delete. Requirements:

  • Input validation with clear 400 responses (zod or manual).
  • Consistent error envelope across all failure modes.
  • Idempotency-Key support on POST /tasks.
  • In-memory store is fine; focus on correctness and API contract, not persistence.
Model SolutionReveal 
import express from 'express';
import { z } from 'zod';
import { randomUUID } from 'crypto';

const app = express();
app.use(express.json());

interface Task { id: string; title: string; done: boolean; }
const tasks = new Map<string, Task>();
const idempotencyResults = new Map<string, Task>();

const TaskInput = z.object({ title: z.string().min(1), done: z.boolean().optional() });

function errorResponse(code: string, message: string) {
  return { error: { code, message } };
}

app.get('/tasks', (req, res) => {
  const limit = Number(req.query.limit ?? 20);
  const after = req.query.after as string | undefined;
  const all = Array.from(tasks.values());
  const startIdx = after ? all.findIndex(t => t.id === after) + 1 : 0;
  const page = all.slice(startIdx, startIdx + limit);
  res.json({ data: page, nextCursor: page.length ? page[page.length - 1].id : null });
});

app.get('/tasks/:id', (req, res) => {
  const task = tasks.get(req.params.id);
  if (!task) return res.status(404).json(errorResponse('NOT_FOUND', 'Task not found'));
  res.json({ data: task });
});

app.post('/tasks', (req, res) => {
  const idKey = req.header('Idempotency-Key');
  if (idKey && idempotencyResults.has(idKey)) {
    return res.status(201).json({ data: idempotencyResults.get(idKey) });
  }

  const parsed = TaskInput.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json(errorResponse('VALIDATION_FAILED', parsed.error.message));
  }

  const task: Task = { id: randomUUID(), title: parsed.data.title, done: parsed.data.done ?? false };
  tasks.set(task.id, task);
  if (idKey) idempotencyResults.set(idKey, task);

  res.status(201).location(`/tasks/${task.id}`).json({ data: task });
});

app.patch('/tasks/:id', (req, res) => {
  const task = tasks.get(req.params.id);
  if (!task) return res.status(404).json(errorResponse('NOT_FOUND', 'Task not found'));
  const parsed = TaskInput.partial().safeParse(req.body);
  if (!parsed.success) return res.status(400).json(errorResponse('VALIDATION_FAILED', parsed.error.message));
  Object.assign(task, parsed.data);
  res.json({ data: task });
});

app.delete('/tasks/:id', (req, res) => {
  if (!tasks.has(req.params.id)) return res.status(404).json(errorResponse('NOT_FOUND', 'Task not found'));
  tasks.delete(req.params.id);
  res.status(204).send();
});

Why this works: validation happens via a schema (zod) rather than scattered manual checks, and every failure path returns the same { error: { code, message } } envelope so clients branch on code reliably. The Idempotency-Key header is checked before validation/creation, so a retried request with the same key returns the original result instead of creating a duplicate task or re-validating.

What interviewers look for beyond the happy path: correct status codes (201 + Location on create, 204 on delete, 404 before 400 on update when the resource doesn't exist), and whether you thought about concurrent requests hitting the same idempotency key at the same time (a real system would need a lock or a unique DB constraint, not just a plain Map check).

Coding Exercise 3.2 — Cursor Pagination

Given an array of 100k timestamped log objects (simulate in memory or SQLite), implement a GET /logs?after=<cursor>&limit=50 endpoint using cursor-based pagination that remains correct even if new logs are inserted between requests.

Model SolutionReveal 
interface LogEntry { id: string; createdAt: number; message: string; }

// Cursor encodes (createdAt, id) so ordering is stable even with duplicate timestamps
function encodeCursor(entry: LogEntry): string {
  return Buffer.from(`${entry.createdAt}:${entry.id}`).toString('base64');
}
function decodeCursor(cursor: string): { createdAt: number; id: string } {
  const [createdAt, id] = Buffer.from(cursor, 'base64').toString().split(':');
  return { createdAt: Number(createdAt), id };
}

app.get('/logs', (req, res) => {
  const limit = Math.min(Number(req.query.limit ?? 50), 200);
  const after = req.query.after as string | undefined;

  let filtered = allLogs; // assume sorted by (createdAt ASC, id ASC)
  if (after) {
    const cursor = decodeCursor(after);
    filtered = allLogs.filter(l =>
      l.createdAt > cursor.createdAt ||
      (l.createdAt === cursor.createdAt && l.id > cursor.id)
    );
  }

  const page = filtered.slice(0, limit);
  const nextCursor = page.length === limit ? encodeCursor(page[page.length - 1]) : null;

  res.json({ data: page, nextCursor });
});

Why this works: the cursor isn't a page number — it's an opaque pointer to "the last row I saw" encoded as (createdAt, id). A composite key is used (not just the timestamp) because timestamps can collide; the tiebreaker id guarantees a strict total order so no row is ever skipped or repeated even if two logs share a timestamp. Because the query is always "give me everything after this exact position" rather than "skip N rows," inserting new rows anywhere in the dataset never shifts what page 2 means — unlike offset pagination, which breaks when rows shift between requests.

Production note: in a real DB this maps directly to a keyset/seek query: WHERE (created_at, id) > ($1, $2) ORDER BY created_at, id LIMIT $3, which uses a composite index efficiently instead of scanning and discarding OFFSET rows.

4. TypeScript Full-Stack Development (Node.js + React) Code it hands-on

Type system depth, async patterns, React rendering model, state management, and Node runtime internals.

4.1 Explain structural typing vs nominal typing. Why does TypeScript use structural typing?Fundamentals

TypeScript compares types by shape (members/structure) rather than by declared name/identity. Two unrelated interfaces with identical members are interchangeable. This matches JavaScript's duck-typed nature and makes gradual typing of existing JS codebases practical. Contrast with nominal typing (Java, C#) where explicit inheritance/declaration is required for compatibility. Follow-up: how do you simulate nominal typing in TS? (branded/opaque types using a private tag field.)

4.2 What's the difference between interface and type? When would you choose one over the other?Fundamentals

Both describe shapes. Interfaces support declaration merging and are generally preferred for public object/API shapes and class contracts. Type aliases can represent unions, tuples, mapped/conditional types — things interfaces cannot express. Practical rule: use interface for extendable object contracts (esp. library-facing), type for unions, utility compositions, and function signatures.

4.3 Explain generics with a practical example (e.g., a typed API client or repository pattern).Type System

Generics let you parameterize types so a function/class preserves the caller's type instead of widening to any/unknown. Example: function fetchJson<T>(url: string): Promise<T> lets consumers get back the exact shape they expect while the implementation stays generic. Discuss constraints (T extends object), default type params, and inference from function arguments.

4.4 What are mapped types and conditional types? Give a use case.Advanced Types

Mapped types transform each property of an existing type (Partial, Readonly, custom {[K in keyof T]: ...}). Conditional types (T extends U ? X : Y) let you branch type-level logic, often combined with infer to extract nested types (e.g., unwrapping a Promise's resolved type). Use case: building a strongly-typed event emitter where the payload type depends on the event name.

4.5 How does the Node.js event loop work, and how does it interact with Promises/async-await under the hood?Node Internals

Single-threaded event loop with phases (timers, pending callbacks, poll, check, close callbacks) plus a microtask queue (Promises, process.nextTick) that drains between phases/after each callback. async/await is sugar over Promises — it doesn't create new threads; CPU-bound work still blocks the loop. Mention worker_threads / child_process for CPU-heavy tasks, and libuv's thread pool for I/O like fs and DNS.

4.6 React: explain the reconciliation algorithm and keys in lists.React

React diffs the new virtual DOM tree against the previous one using heuristics: different element types → full remount; same type → compare props/attributes and recurse into children. Keys give list items stable identity across renders so React can match/reorder/reuse DOM nodes instead of destroying and recreating them (avoiding lost state, unnecessary re-mounts). Common pitfall: using array index as key when list order can change.

4.7 Compare useMemo, useCallback, and React.memo. When do they actually help performance?React Performance

useMemo memoizes a computed value; useCallback memoizes a function reference; React.memo skips re-rendering a component if props are shallow-equal. They only help when the memoized value/function is expensive to recompute OR passed to a memoized child / dependency array where referential equality matters. Overusing them adds complexity and memory overhead without measurable gains — profile first.

4.8 Explain the differences between REST calls from a React app using fetch vs a library like React Query/SWR, and why caching layers matter.Frontend Data

Raw fetch gives no caching, dedup, retries, or stale-while-revalidate semantics — you re-implement loading/error/race-condition handling manually. React Query/SWR provide cache keys, background refetching, request de-duplication, optimistic updates, and pagination helpers, reducing boilerplate and preventing stale UI / race conditions on fast navigation.

4.9 How would you type a discriminated union for handling async request states (idle/loading/success/error)?Type System + React 
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: string };

The discriminant (status) lets TypeScript narrow the union inside conditionals/switches, so data is only accessible when status === 'success'. This is the idiomatic replacement for loose booleans like isLoading/isError that can represent impossible states simultaneously.

Coding Exercise 4.1 — Typed Debounce Hook

Implement a generic useDebouncedValue<T>(value: T, delayMs: number): T React hook in TypeScript with no external dependencies.

  • Must clean up timers on unmount / value change (no memory leaks).
  • Must be strongly typed for any value type T.
  • Bonus: add an optional leading flag to fire immediately on first change.

Evaluates: hooks lifecycle, generics, cleanup functions, edge cases (rapid updates, unmount during pending timer).

Model SolutionReveal 
import { useEffect, useRef, useState } from 'react';

function useDebouncedValue<T>(value: T, delayMs: number, leading = false): T {
  const [debounced, setDebounced] = useState<T>(value);
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
  const isFirstRef = useRef(true);

  useEffect(() => {
    if (leading && isFirstRef.current) {
      isFirstRef.current = false;
      setDebounced(value);
      return;
    }

    timerRef.current = setTimeout(() => {
      setDebounced(value);
    }, delayMs);

    return () => {
      if (timerRef.current) clearTimeout(timerRef.current);
    };
  }, [value, delayMs, leading]);

  return debounced;
}

Why this works: the cleanup function returned from useEffect clears the pending timer whenever value changes again before the delay elapses, or on unmount — this is what prevents the classic bug of a stale setDebounced firing after the component is gone or after a newer value has already superseded it. The generic T is inferred from the argument, so it works for strings, objects, arrays, etc. with no any. The leading flag uses a ref (not state) to track "have we fired the first update yet" without triggering an extra render.

Common mistakes to watch for: forgetting the cleanup (memory leak / stale updates), putting debounced itself in the dependency array (infinite loop), or using setInterval instead of setTimeout.

Coding Exercise 4.2 — Typed Event Emitter

Build a type-safe EventEmitter class where each event name maps to a specific payload type, enforced at compile time (no any).

interface Events {
  userCreated: { id: string; email: string };
  userDeleted: { id: string };
}
const emitter = new TypedEmitter<Events>();
emitter.on('userCreated', (payload) => { /* payload typed correctly */ });
emitter.emit('userDeleted', { id: '123' }); // compile error if shape wrong

Evaluates: mapped/generic types, keyof, function overload inference.

Model SolutionReveal 
type Listener<T> = (payload: T) => void;

class TypedEmitter<Events extends Record<string, unknown>> {
  private listeners: {
    [K in keyof Events]?: Array<Listener<Events[K]>>
  } = {};

  on<K extends keyof Events>(event: K, listener: Listener<Events[K]>): void {
    const arr = this.listeners[event] ?? [];
    arr.push(listener);
    this.listeners[event] = arr;
  }

  off<K extends keyof Events>(event: K, listener: Listener<Events[K]>): void {
    const arr = this.listeners[event];
    if (!arr) return;
    this.listeners[event] = arr.filter(l => l !== listener);
  }

  emit<K extends keyof Events>(event: K, payload: Events[K]): void {
    (this.listeners[event] ?? []).forEach(l => l(payload));
  }
}

Why this works: the class is generic over an Events map, and every method uses K extends keyof Events so TypeScript ties the event name to the exact payload type via Events[K] — passing the wrong payload shape for a given event name is a compile-time error, not a runtime surprise. No any is needed anywhere.

Follow-ups interviewers ask: how would you add a once() method (wrap the listener, unsubscribe after first call)? How would you support wildcard/catch-all listeners without breaking the type safety (harder — usually requires a separate loosely-typed channel)?

Coding Exercise 4.3 — Node.js Rate Limiter Middleware

Write an Express (or Fastify) middleware implementing a sliding-window rate limiter per IP, in-memory (no Redis), fully typed, with configurable window and max requests. Discuss how you'd make it distributed-safe across multiple Node instances (segue into Microservices/System Design sections).

Model SolutionReveal 
import { Request, Response, NextFunction } from 'express';

interface RateLimitOptions {
  windowMs: number;
  max: number;
}

function slidingWindowRateLimiter({ windowMs, max }: RateLimitOptions) {
  const hits = new Map<string, number[]>(); // ip -> timestamps

  return (req: Request, res: Response, next: NextFunction) => {
    const ip = req.ip ?? 'unknown';
    const now = Date.now();
    const windowStart = now - windowMs;

    const timestamps = (hits.get(ip) ?? []).filter(t => t > windowStart);
    timestamps.push(now);
    hits.set(ip, timestamps);

    if (timestamps.length > max) {
      res.setHeader('Retry-After', Math.ceil(windowMs / 1000).toString());
      return res.status(429).json({
        error: { code: 'RATE_LIMITED', message: 'Too many requests' }
      });
    }

    next();
  };
}

Why this works: instead of a fixed counter that resets at a hard boundary (fixed window, which allows bursts right at the edge of two windows), this keeps a rolling list of hit timestamps per IP and filters out anything older than windowMs on every request — an accurate sliding window log. Trade-off: memory grows with request volume per key; a production version would cap the array size or switch to a sliding window counter approximation.

Distributed-safe follow-up (what interviewers want you to raise unprompted): this in-memory Map only works per Node process. Across multiple instances behind a load balancer, each instance has its own counter, so the effective limit is max × instanceCount. Fix: move the counter to a shared store (Redis) using an atomic INCR + EXPIRE or a Lua script, or push rate limiting up to the API Gateway layer entirely.

5. Cloud Platforms & CI/CD Vocabulary-heavy — cram last

Deployment pipelines, infra-as-code, containers/orchestration, and observability.

5.1 Walk through a typical CI/CD pipeline for a Node.js/React monorepo.CI/CD

CI on PR: install deps (cached), lint, type-check, unit tests, build, maybe preview deploy. On merge to main: build production artifacts/Docker images, tag with commit SHA, push to a registry, run integration/e2e tests against a staging environment, then deploy (blue-green/canary/rolling) to production with automated rollback on health-check failure. Emphasize: pipeline should fail fast (cheap checks like lint before expensive e2e), and deployments should be reproducible from any commit.

5.2 Blue-green vs canary vs rolling deployments — trade-offs?Deployment Strategy

Blue-green: two full environments, switch traffic instantly, easy instant rollback, but double infra cost during cutover and doesn't catch issues gradually. Canary: route a small % of traffic to the new version, monitor metrics, gradually increase — catches regressions before full exposure, but needs good metrics/automation to be safe and takes longer. Rolling: replace instances gradually (default in Kubernetes deployments) — no extra infra cost, but rollback is slower and you briefly run mixed versions, which requires backward-compatible APIs/schemas.

5.3 What is Infrastructure as Code, and why prefer it (e.g., Terraform/CDK) over manual console changes?IaC

Infra defined declaratively in version-controlled files, enabling code review, reproducibility across environments, drift detection, and disaster recovery (rebuild from code). Manual console changes are untracked, unreviewable, and prone to environment drift between staging/prod. Discuss state management challenges in Terraform (remote state, locking to prevent concurrent applies) and CDK's advantage of using real programming languages for reuse/abstraction.

5.4 Explain the difference between a container and a VM, and why Kubernetes exists.Containers

VMs virtualize hardware and run a full guest OS per instance (heavier, stronger isolation); containers share the host kernel and isolate at the process level (namespaces/cgroups), making them lightweight and fast to start. Kubernetes solves the problem of running many containers reliably across a cluster of machines: scheduling, self-healing (restarting failed containers), scaling, service discovery, rolling updates, and declarative desired-state management.

5.5 How do you manage secrets (API keys, DB credentials) in a cloud-native CI/CD pipeline?Security

Never commit secrets to source control. Use a secrets manager (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault) injected at runtime or deploy time; CI systems have their own encrypted secret stores (GitHub Actions secrets) for pipeline-time credentials. Rotate regularly, scope permissions minimally (least privilege IAM roles per service), and audit secret access. For Kubernetes, discuss Secrets objects (base64, not encrypted at rest by default — pair with encryption at rest or an external secrets operator).

5.6 What would you monitor in production for a distributed system, and what's the difference between monitoring and observability?Observability

Monitoring = watching known metrics/dashboards for known failure modes (CPU, error rate, latency percentiles — the "three pillars": metrics, logs, traces). Observability = the ability to ask new questions about system behavior you didn't anticipate, using high-cardinality structured data (distributed tracing across services, e.g., OpenTelemetry, to follow one request across multiple microservices). Discuss SLIs/SLOs/error budgets as the framework connecting monitoring to business reliability goals.

5.7 How would you design a zero-downtime database migration as part of a deployment?Migrations

Use the expand/contract (parallel change) pattern: (1) expand — add new column/table without removing old, deploy code that writes to both; (2) backfill existing data; (3) migrate reads to the new structure; (4) contract — once all instances are on new code and backfill is verified, remove the old column/table. This avoids the classic problem where a schema migration and a rolling code deploy overlap and old-version pods break against the new schema (or vice versa).

Coding Exercise 5.1 — Write a CI Pipeline Config

Write a GitHub Actions workflow (YAML) for a Node.js/TypeScript monorepo (frontend + backend) that: installs deps with caching, runs lint + type-check + unit tests in parallel jobs, builds Docker images tagged with the commit SHA on merge to main, and pushes to a registry. Include a manual approval gate before a production deploy job.

Model SolutionReveal 
name: CI/CD

on:
  push:
    branches: [main]
  pull_request:

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'npm' }
      - run: npm ci
      - run: npm run lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'npm' }
      - run: npm ci
      - run: npm run typecheck

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'npm' }
      - run: npm ci
      - run: npm test -- --ci

  build-and-push:
    needs: [lint, typecheck, test]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

  deploy-production:
    needs: build-and-push
    runs-on: ubuntu-latest
    environment:
      name: production   # requires manual approval configured on this GitHub Environment
    steps:
      - run: echo "Deploying ${{ github.sha }} to production"

Why this works: lint/typecheck/test run as separate parallel jobs (not sequential steps in one job) so the pipeline fails fast and gives independent, clearly-labeled status checks; they all gate build-and-push via needs. The image is tagged with github.sha, not latest, making every deploy traceable back to an exact commit. The manual approval gate is implemented via a GitHub Environment named production with required reviewers configured in repo settings — the job simply pauses until someone approves it, no extra scripting needed.

Follow-ups: how would you add a staging environment that deploys automatically but production requires approval? (Two separate environment: blocks, only production has required reviewers.) How would you cache Docker layers to speed up builds? (cache-from/cache-to with type=gha in build-push-action.)

Coding Exercise 5.2 — Kubernetes Manifest Review/Fix

Given a flawed Deployment + Service YAML (no resource limits, no readiness/liveness probes, latest image tag, single replica), identify every production-readiness issue and rewrite the manifest correctly.

Model SolutionReveal

Issues to identify (say these out loud before showing the fix):

  • image: myapp:latest — not reproducible/rollback-unsafe; a redeploy can silently pull a different image than what was tested.
  • No resources.requests/limits — the pod can starve other workloads (no requests) or get OOMKilled unpredictably (no limits); the scheduler also can't bin-pack effectively without requests.
  • No readinessProbe — Kubernetes will route traffic to a pod before it's actually ready to serve, causing errors during startup/rolling updates.
  • No livenessProbe — a hung/deadlocked process never gets restarted automatically.
  • replicas: 1 — single point of failure; any node/pod restart causes a full outage.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels: { app: myapp }
  template:
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: myapp
          image: myapp:1.4.2   # pinned, immutable tag (or digest) — never :latest
          ports:
            - containerPort: 8080
          resources:
            requests: { cpu: '250m', memory: '256Mi' }
            limits: { cpu: '500m', memory: '512Mi' }
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 15
            periodSeconds: 20
---
apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  selector: { app: myapp }
  ports:
    - port: 80
      targetPort: 8080

Why this works: replicas: 3 plus the readiness probe means a rolling update never drops all pods at once and never sends traffic to a pod that isn't ready yet. Requests/limits let the scheduler place pods sensibly and protect the node from a single runaway container, while the liveness probe recovers from hangs automatically instead of requiring manual intervention.

Bonus points interviewers look for: mentioning a PodDisruptionBudget (so voluntary disruptions like node drains don't take down too many replicas at once) and a HorizontalPodAutoscaler tied to CPU/memory or custom metrics for actual traffic-based scaling.
